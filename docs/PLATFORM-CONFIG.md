# Native shell configuration

The native projects (`/android`, `/ios`) are generated by `npx cap add` and are
gitignored, so anything the shells need has to be recorded here and reapplied
after a regeneration. **Without the entries below the voice games fail silently
on device while passing every test in CI.**

---

## Android — `android/app/src/main/AndroidManifest.xml`

```xml
<uses-permission android:name="android.permission.RECORD_AUDIO" />

<!-- The app never places calls or reads telephony state; declare that the
     microphone is the only audio capture we do, so Play's review does not
     assume more. -->
<uses-feature android:name="android.hardware.microphone" android:required="false" />
```

`android:required="false"` matters: a tablet with no microphone must still be
able to install the app, because four of the five pillars do not need one.

Android 6+ also needs the **runtime** prompt. Capacitor's WebView does not raise
it automatically for `getUserMedia`; the host Activity must grant the WebView
permission request. Either add `@capacitor-community/speech-recognition`-style
handling or override `onPermissionRequest` in `MainActivity`:

```java
webView.setWebChromeClient(new BridgeWebChromeClient(bridge) {
  @Override public void onPermissionRequest(final PermissionRequest request) {
    request.grant(request.getResources());
  }
});
```

…gated behind an `ActivityCompat.requestPermissions` call for `RECORD_AUDIO`.

## iOS — `ios/App/App/Info.plist`

```xml
<key>NSMicrophoneUsageDescription</key>
<string>Lumi measures how loud you are in the voice games. No recording is made and nothing is saved or sent anywhere.</string>
```

Apple rejects any app that touches the microphone without this string, and for
a Kids Category app the wording is read by a human reviewer. Say what is
measured and say what is *not* kept — vague strings ("for a better experience")
get rejected.

## Both platforms

- **No ad SDKs, no analytics SDKs, no third-party SDKs of any kind.** Apple's
  Kids Category forbids third-party analytics and advertising outright, and
  bars sending any personally identifiable or device information to third
  parties. We currently ship `react` and `react-dom` and nothing else; keep it
  that way.
- **`AudioContext` must be created or resumed inside a user gesture.** Both
  WebViews are stricter than desktop Chromium. The voice games already start
  the meter from a button press; do not move it to mount.
- **Offline.** The shells load from the bundle, so there is no network
  dependency to configure and no ATS/cleartext exception needed.

## Verification the sandbox cannot do

This environment has Java and Gradle but **no Android SDK and no macOS**, so
neither shell has ever been built here. `getUserMedia` also cannot be tested:
the sandbox has no audio stack, so Chromium cannot synthesise even a fake
microphone (`NotFoundError: Requested device not found`). The voice path is
covered by 162 unit tests and by the no-microphone fallback, which the browser
smoke does exercise — but the live meter itself is unverified until someone
runs it on a handset.
